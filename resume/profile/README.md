# Profile

A repository of personal content used as raw material for resumes, cover letters, recruiter call prep, and interviews.

**Start here:** read [narrative.md](narrative.md) first — it's the backbone every other file builds on. See also the top-level [`resume/README.md`](../README.md) for how these files fit into the wider skill workflow.

## Two versions

| Folder | Purpose | Audience |
|---|---|---|
| `profile/` (this folder) | Concise, token-optimised | Agent skills (`adapt-resume`, `prep-recruiter-call`) |
| [`profile/verbose/`](verbose/) | Full prose, human-readable | Personal reference, self-reflection, editing |

**When editing your profile:** update `verbose/` first (easier to write and read), then distil the key facts back into the concise version here.

## Subfolders

| Folder | Purpose |
|---|---|
| [verbose/](verbose/) | Full-prose version of the concise files above — write here first |
| [academic/](academic/) | Material only relevant to teaching/academic applications, e.g. [teaching-statement.md](academic/teaching-statement.md) — kept out of the main folder since no skill reads it automatically |
| [quarterly_reviews/](quarterly_reviews/) | Raw performance review PDFs, plus [summary.md](quarterly_reviews/summary.md) distilling recurring themes and quotable metrics across cycles |
| [sources/](sources/) | Raw source files behind a derived `.md` elsewhere in this folder — assessment PDFs, feedback exports. Kept so a summary can be re-derived or re-checked later; nothing here is read directly by a skill |

Whenever a derived file (`personality.md`, `interview-feedback.md`, `quarterly_reviews/summary.md`) is distilled from a raw artifact, keep the raw artifact in `sources/` or its own subfolder rather than discarding it — the summary decays faster than the source stays useful.

## What to write yourself

The highest-leverage files to keep current:

1. **`narrative.md`** — the one story that connects every role
2. **`star-stories.md`** — real lived stories by theme; these make recruiter prep far richer than anything derived from resume bullets
3. **`interview-feedback.md`** — update after every rejection with real feedback; this is what turns a string of rejections into a specific, fixable pattern instead of a vague feeling that something's wrong

## Building your own version of this system

If you're setting up an equivalent profile folder for yourself, these are the components worth having, roughly in the order they start paying off:

1. **A concise/verbose split.** Write the long, honest version first (`verbose/`) — it's easier to think out loud in full sentences. Then distil each file down to the terse version an agent actually reads. Skip the distillation step and every skill run burns tokens re-reading paragraphs for one fact.
2. **A narrative backbone (`narrative.md`).** One file that answers "tell me about yourself" in your own words. Everything else — cover letters, opening hooks, STAR framing — should be consistent with this, not reinvent your story per application.
3. **Values and motivations as explicit filters (`values.md`, `motivations.md`), not just aspirations.** The useful version names actual green/red flags and what you're optimising for right now, specific enough that a role can genuinely fail the test. "Good culture" isn't a filter; "no dedicated data function" is.
4. **Real stories, not resume bullets (`star-stories.md`).** Resume bullets are already compressed for space; they make poor interview prep source material because the texture is gone. Write stories in full before you need them, organised by theme so they can be matched to whatever a JD emphasises.
5. **A feedback loop, not just a stories archive (`interview-feedback.md`, `skills-to-learn.md`).** The highest-value files in this whole folder are the ones populated by outcomes rather than self-reflection: what recruiters and hiring managers actually said, and which specific gaps keep recurring across applications. Self-assessment plateaus; adversarial feedback (rejections, reviews) keeps surfacing blind spots.
6. **Logistics as its own file (`logistics.md`).** Notice period, visa status, salary range, location constraints — dull facts that are asked constantly and easy to misstate under pressure if not written down once, precisely.
7. **Raw source material kept alongside its derived summary.** Performance reviews, assessment results, peer feedback exports — don't just extract the summary and discard the original. The summary decays in usefulness faster than you'd expect; the raw file lets you re-mine it later with fresh eyes or a different question in mind.
